## Keputusan Rewrite Modul Cuti

- **Struktur paket repositories → split-by-technology, JPA flat di `jpa/`** (ikut decisions-pegawai §33). Semua repo JPA cuti (`CutiPegawaiRepository`, `CutiJenisRepository`, `CutiKuotaRepository`, `CutiApprovalRepository`, dan child-entity repo `CutiApprovalChainRepository`, `CutiKlaimDetailRepository`) pindah **flat ke `repositories/cuti/jpa/`** — bukan per-aggregate. JOOQ tetap di `repositories/cuti/jooq/`. **`CutiApprovalChainCustomRepository(+Impl)` dihapus** (CriteriaBuilder `findPageApproval` hanya dipakai facade yang mati); `extends ...CustomRepository` dicabut dari `CutiApprovalChainRepository`.

- **Buang trio facade interface (`CutiPengajuanService`/`CutiApprovalService`/`CutiApprovalChainService` + `*Impl`)** — no interface kecuali benar-benar perlu (ikut decisions-pegawai). Ketiganya cuma delegasi ke Command + re-wrap `try/catch → SavedStatus.FAILED` (langgar ADR-0021, cegah rollback) dan masih `findPage` via Specification legacy. Controller diarahkan langsung ke Command (`PengajuanCutiCommand`/`ApprovalCutiCommand`/`KlaimCutiCommand`) untuk tulis, dan ke `*QueryService` untuk baca. Generator rantai approval (`generateApprovalChain`/`generateApprovalKlaimChain` di `CutiApprovalChainServiceImpl`) dipindah ke `CutiApprovalChainGenerator` (@Component non-interface, `forPengajuan()`+`forKlaim()`) — bukan private helper di `PengajuanCutiCommand`, karena dipanggil dua command tanpa caller bersama.

- **Mapper read Pola B untuk SEMUA read cuti (termasuk inbox)**: ekstrak `mapToResponse`/`mapToMiniResponse` inline (Pola A) dari `CutiPengajuanQueryRepository` ke `CutiPegawaiJooqMapper` (kelas `final` static, ctor privat, **bukan** `@Component`); inbox juga pakai mapper Pola B. Buang `.from(entity)` dari `CutiPengajuanResponse`, `CutiApprovalMiniResponse`, `CutiApprovalChainResponse` — perakitan response pindah ke mapper JOOQ. (`JenisCutiResponse`/`JenisCutiMiniResponse` sudah terhapus — §29 tuntas.)

- **Read approval-history (`GET /cuti/approval/{cutiId}`) → `CutiApprovalQueryService` + JOOQ**. Endpoint ini (riwayat approver per satu pengajuan: list `CutiApproval`) tidak punya pengganti JOOQ saat facade dibunuh, dan datanya **tidak** ada di detail pengajuan (`CutiPengajuanResponse` hanya bawa `approvalCutiStatus`+`approvalLevel` agregat, bukan daftar approver). Keputusan: buat `CutiApprovalQueryService` + entry di JOOQ repo (`CutiApprovalQueryRepository`/`CutiApprovalJooqMapper` Pola B), bukan embed nested-list ke read root (lawan mini-projection ADR-0001). Controller `CutiApprovalController` di-split: tulis→`ApprovalCutiCommand`/`KlaimCutiCommand`, baca→`CutiApprovalQueryService`.

- **Penamaan kelas write Cuti Pegawai → `Cuti<Operasi>CommandService`** (selaras konvensi seluruh codebase `<Aggregate>CommandService`/`<Aggregate>QueryService`). Tiga outlier di-rename: `PengajuanCutiCommand`→`CutiPengajuanCommandService`, `ApprovalCutiCommand`→`CutiApprovalCommandService`, `KlaimCutiCommand`→`CutiKlaimCommandService` — berpasangan rapi dengan `*QueryService` yang sudah ada. Write Cuti Pegawai tetap **3 kelas terpisah per-operasi** (§9), bukan satu `CutiPegawaiCommandService` — pemecahan per-operasi sah, hanya sufiks/urutan-kata yang diseragamkan. `CutiApprovalChainGenerator` (Q2) tetap di luar pola Command/Query (helper, bukan entry write).

- **Page-request DTO → `*IndexQuery extends PagedRequest`, buang Specification dead**. Lima DTO read `extends CommonPageRequest` di-rename & re-base ke `PagedRequest` (ikut konvensi rewrite): `CutiPengajuanRequest`→`CutiPengajuanIndexQuery`, `CutiApprovalRequest`→`CutiApprovalIndexQuery`, `CutiJenisRequest`→`CutiJenisIndexQuery`, `CutiKuotaRequest`→`CutiKuotaIndexQuery`, `CutiApprovalChainRequest`→**`CutiApprovalChainIndexQuery`** (pertahankan nama entity, bukan `Inbox`). `getSpecification()`/`getApprovalChainSpecification()` + helper CriteriaBuilder (`createTahunPredicate`/`createYearPredicate`) + import `jakarta.persistence.criteria.*` & `SpecificationBuilder` **dibuang** — sisakan field filter POJO + validasi (`@NotNull`/`@Min`). **Verified per-field (2026-06-30)**: JOOQ baca field via `baseWhere(query)`, BUKAN spec; 4 dari 5 (`Pengajuan`/`ApprovalChain`/`Jenis`/`Kuota`) sudah ter-port penuh ke `baseWhere` (termasuk koreksi bug `MONTH`→`YEAR` di pengajuan). **Pengecualian `CutiApprovalIndexQuery`**: `getSpecification`-nya (filter `id`/`cutiId`/`approverId`/`jabatanId`) adalah **spesifikasi forward** untuk `CutiApprovalQueryRepository` baru (Q5) — keempat field WAJIB diport ke `baseWhere` JOOQ baru sebelum spec lama dihapus. Catatan: `getSpecification()` di `CutiJenisPostRequest`/`CutiKuotaPostRequest`/`CutiKuotaImportRequest` **TETAP** (dipakai guard `exists()` write-side) — jangan disentuh.

**Refactor `/list` (2026-07-31)**: `GET /cuti/jenis/list` kini pakai **`CutiJenisListRequest`** (`{parentId, nama}`, filter-only, TIDAK extends `PagedRequest`) — baru, terpisah dari DTO read index (`CutiJenisRequest`/`CutiJenisIndexQuery` yang tetap extends `PagedRequest`). Sort `listQuery` hardcoded `.orderBy(CUTI_JENIS.NAMA.asc())`.

- **Tiga aggregate, multi-command per akar**: modul cuti dipecah jadi **tiga aggregate** — **Jenis Cuti**, **Kuota Cuti**, dan **Cuti Pegawai** (akar). `CutiApproval`, `CutiApprovalChain`, dan `CutiKlaimDetail` **bukan aggregate terpisah** melainkan **child entity** di bawah Cuti Pegawai. **Sisi tulis Cuti Pegawai dipecah per-operasi**: `PengajuanCutiCommand` (alur Pengajuan), `KlaimCutiCommand` (alur Klaim), `ApprovalCutiCommand` (proses approve/reject/return), dan generator rantai approval sebagai helper internal.

- **Sisi baca → JOOQ penuh + mini-projection** (ikut ADR-0001): `CutiPegawaiJooqRepository` (index pengajuan + inbox approval), `CutiKuotaJooqRepository`, `CutiJenisJooqRepository`. Tiap `*Response` **tetap nested** demi kompat FE, tapi tiap objek nested = **mini-projection** `row(id+label)`. **Inbox approval**: `CutiApprovalChainCustomRepositoryImpl` (CriteriaBuilder) **dibuang**, diganti query JOOQ `GROUP BY ref_cuti_id` + `max(read_write_status)`. **Bug diperbaiki saat port**: filter `tahun` di `CutiPengajuanRequest` salah pakai `MONTH(tanggal_mulai)`, dikoreksi jadi `YEAR(tanggal_mulai)`.

- **ID konfigurasi cuti → `CutiProperties` typed bean** (`@ConfigurationProperties(prefix="app.cuti")`): legacy menyebar ID hardcoded lewat `@Value`/`DefConfig` di 4+ kelas. Satu bean `CutiProperties` dengan grup `jenisCuti` (tahunan/besar/ibadah), `jabatan` (supervisorSdm/managerSdm/direkturUtama/direkturUmum), `level` (staff/supervisor/manager/dst.). **Field jenis-cuti dipindah keluar dari `DefConfig`** — `DefConfig` menyisakan `PROTECTED_KARTU_IDENTITAS_ID` saja.

- **Generator rantai approval → unifikasi data-driven + satu pointer-init** (helper internal di bawah `PengajuanCutiCommand`). Tiga metode hampir duplikat legacy (`levelStafList`/`levelSupervisorList`/`levelManagerList`) diringkas jadi **satu rutin `initPointer(slots)`** dengan daftar slot sebagai data. **Bug latent diperbaiki**: slot statis (SDM/direksi) kini dicek `existsByJabatanId` (sama seperti slot dinamis) — jabatan SDM kosong tak lagi memblokir rantai. Rantai **klaim** tetap terpisah (hanya `supervisorSdm`, langsung `WRITE`+`PENDING`).

- **Alokasi kuota & date-bucketing → math murni di `CutiKuotaAllocator`, `SaveCutiService` (267 baris) dipecah per seam-tahun (REVISI: 6 handler dipertahankan eksplisit, TIDAK dilebur 6→1)**. Niat awal §29 (lebur enam metode entry jadi satu fungsi data-driven) **direvisi** — tiap handler periode mengkode aritmetika-tahun halus & ter-audit yang berbeda nyata (`forNextYear` pakai `mulai.year−1` yang **benar** di sisi reservasi; `between30JunAnd1Jul` punya split `totalCutiJuni`; `saveCutiNonTahunan` special-case Ibadah). Meleburnya berisiko regresi → lawan "no AI SLOP". Keputusan (simetris [[decisions-cuti]] Q9 klaim): **pertahankan 6 handler eksplisit, pecah file via seam 30-Jun/1-Jul** = batas siklus-hidup kuota (lihat fakta kuota di bawah). Tiga file: **(1) `CutiReservasiCrossYearService`** = `forNextYear`/`overlappingYear`/`separateCutiWithNextYear` (~70); **(2) `CutiReservasiInYearService`** = `between1JanAnd30Jun`/`between1JulAnd31Dec`/`between30JunAnd1Jul`/`saveCutiNonTahunan`/`separateCutiWithPreviousYear` (~115); **(3)** helper `applyAllocation`+`setPic` shared. `CutiKuotaAllocator` **tetap pure-math** (sudah diekstrak). `totalCutiJuni` (`between30JunAnd1Jul:157`) pindah dari `DateHelper.countWeekdaysBetween`(dihapus §47) ke `WorkdayCalculator.count`. **Bug diperbaiki saat port** (`saveCutiNonTahunan`): `setKuotaAwal(...)` dipanggil dobel & cabang `else` tak pernah set `kuotaAkhir`.

- **Siklus-hidup kuota cuti: di-set 1 Juli, expired 30 Juni tahun berikutnya** (info domain user, 2026-06-30). Karena itu boundary **30 Jun / 1 Jul** di handler reservasi & settlement **bukan tanggal arbitrer** melainkan batas siklus kuota — menjelaskan filter `expiredGreaterThan` (`separateCutiWithPreviousYear:221`, `between30JunAnd1Jul:142`) dan kenapa periode di-bucket di tanggal itu. Glossary: lihat [[language-cuti]].

- **State-machine approval → restrukturisasi per ADR-0021 + helper transisi murni**. Legacy `CutiApprovalServiceImpl.savePengajuan`/`saveKlaim` membungkus seluruh body dalam `try/catch → SavedStatus.FAILED` (anti-pola: exception tertangkap di dalam → **tx tak rollback**). Keputusan: metode transisi internal **melempar bebas** (tak swallow); hanya **satu entry publik `@Transactional`** di `ApprovalCutiCommand` yang membungkus hasil ke `SavedStatus`. Ekstrak advance/retreat pointer jadi **helper transisi murni**. **Buang `save()` redundan** (4× manual di `doSaveAcceptReject`) — andalkan dirty-checking dalam tx. CSRF idempotency tetap, tapi jadi **guard di entry** + rename `validateToken`→`isTokenAlreadyUsed`.

- **Idempotency token (CSRF single-use Redis) → guard seragam di semua entry + `DUPLICATE` konsisten**. Guard diaktifkan di **semua** command tulis cuti (termasuk `klaim()` create yang dikomentari di legacy). Kembalikan `ESaveStatus.DUPLICATE` konsisten (bukan throw). Rename helper jadi `isTokenAlreadyUsed`/`consumeToken`. Pertahankan TTL 5 menit & mekanisme Redis; token tetap di **request body**.

- **Perbaiki target `@SQLDelete` `CutiApproval` ke `cuti_approval`** dan **pertahankan `@Audited`+soft-delete** — `CutiApproval` adalah jejak audit keputusan yang paling butuh histori. `CutiApprovalChain` & `CutiKlaimDetail` tetap child murni.

- **Pembatalan vs `delete()` → buang stub, hanya `cancel()` (`→ CANCELED`)**. Legacy `delete(id)` adalah **stub `return false`** (dead code). Dihapus; satu-satunya jalur "hapus" adalah `pembatalan`, di-rename `cancel()`.

- **Deduksi kuota saat approval (`CutiKuotaUpdateByCutiService`) → port 1:1, bug `now()` SENGAJA dipertahankan**. Klasifikasi periode berbasis `LocalDate.now()` di sisi deduksi: bug lintas-tahun dipertahankan (parity), dilacak sebagai **beads issue terpisah**. ⚠️ Buat issue `bd` untuk bug `LocalDate.now()` deduksi kuota lintas-tahun sebelum/selagi porting service ini.

- **Aggregate Jenis & Kuota → Command+Query standar, Excel di sisi Command**. **CutiJenis**: flat CRUD (tree entity tapi service flat — response cuma bawa `parent` mini). **CutiKuota**: CRUD + `importData` (POI HSSF/XSSF) + `exportTemplate` (POI SXSSF) + `findByPegawai`. Import & template-build tetap di sisi Command. **Konsolidasi DTO Jenis**: **satu `CutiJenisMiniResponse {id,nama}`** dipakai di mana pun; **buang `JenisCutiMiniResponse` & `JenisCutiResponse`**.

- **Layanan validasi pengajuan → validator kolaborator khusus, `existsBy` eksplisit, aturan minimal jadi fungsi murni**. Tiga perbaikan saat port: (1) **buang Specification-on-DTO** → query derived eksplisit; (2) **`validateMinimalCuti` jadi fungsi murni statik** (`MinimalCutiRule.check(totalHariKerja, totalSisaKuota)`); (3) **inject `CutiProperties`** ganti `DefConfig`.

- **Layout controller — pertahankan kontrak URL persis, 4 controller, buang `CutiController` kosong**. Tiap controller inject `*Query` + `*Command` yang relevan. `CutiPengajuanController` boleh inject ≥2 command (FE URL-prefix melayani >1 operasi aggregate). **Inbox tetap di `/cuti/pengajuan/approval`** tapi diarahkan ke `CutiPegawaiQuery`. **Guard tanggal boundary tetap di controller** (`@Valid`+`Errors`+`ErrorResult.build`).

- **Kalkulasi hari kerja → satu fungsi murni, perbaiki bug double-subtract**. Legacy `DateHelper.countWeekdaysBetween` − `hariLiburRepository.countBy...` **terduplikasi di 3 titik** + bug: hari libur jatuh Sabtu/Minggu tetap dikurangi → undercount. Keputusan: **ekstrak satu fungsi murni** `WorkdayCalculator.count(tglMulai, tglSelesai, Set<LocalDate> libur)` dengan logika `getWorkingDays` yang benar (bukan-weekend DAN bukan-libur), perbaiki bug double-subtract, hapus duplikasi.

- **`jumlahHari` di pengajuan = bug weekday-only → satukan ke nilai hari-kerja (holiday-adjusted)**. Entity `CutiPegawai` punya dua kolom: `jumlahHari` & `jumlahHariKerja`. **Verified (2026-06-30, grep)**: `getJumlahHari` (non-Kerja) **hanya dibaca untuk display** (`CutiPengajuanResponse:37`, `CutiPengajuanMiniResponse:65`) — **tak ada konsumen logika**; semua logika (deduksi kuota `SaveCutiService` ×6, `MinimalCutiRule`/sisa-kuota `CutiPengajuanValidator`, guard & settle klaim `KlaimCutiCommand` ×10) baca `getJumlahHariKerja`. Legacy `PengajuanCutiCommand` menyetel `jumlahHari = countWeekdaysBetween` (weekday-only, **tak** potong libur) sehingga utk contoh 12–17 Jun 2026 menghasilkan **4**, padahal ekspektasi domain = **3** (potong Sab/Min 13–14 + libur 16). Klaim sudah benar (set `jumlahHari = jumlahHariKerja`). **Keputusan**: pengajuan menyetel **`jumlahHari` = `jumlahHariKerja` = `WorkdayCalculator.count(...,libur)`** (satu angka hari-kerja). Konsekuensi: **(a)** TIDAK perlu overload 2-arg `WorkdayCalculator` — cukup `count` 3-arg; **(b)** `DateHelper.countWeekdaysBetween` **dibuang total** (tak ada konsumen tersisa); **(c)** aman utk FE — `jumlahHari` murni display, tak ada logika server yang andalkan nilai mentahnya. Kolom DB `JUMLAH_HARI` **dipertahankan** (kompat FE/JOOQ read), hanya nilainya dikoreksi — bukan migrasi skema.

- **Strategi mapper → Pola B (kelas `*Mapper`) konsisten rewrite**. Legacy cuti pakai Pola A (`Response.from(entity)` yang lazy-load). Rewrite memakai Pola B: `mapper/cuti/<aggregate>/CutiJenisMapper` (toEntity/updateEntity), response baca dirakit `CutiPegawaiJooqMapper`/`CutiKuotaJooqMapper`/`CutiJenisJooqMapper`. **`refCuti`** dirakit via **JOOQ self-join** ke `cuti_pegawai` (bukan `entity.getRefCuti()` lazy-load).

- **`KlaimCutiCommand` (359 baris) dipecah 4 kelas per seam operasi+tahun** (CODING_RULES §4 ≤120 ketat — lihat [[feedback-max-line]]). Legacy meng-inline 3 tanggung jawab lintas-operasi ke satu kelas. Pecah jadi: **(1) `CutiKlaimCommandService`** = `save`+`update` (submission klaim oleh pegawai: bangun `CutiPegawai` klaim + `CutiKlaimDetail`, `getWorkingDays` list-based, generate chain klaim) ~85 baris; **(2) `CutiKlaimApprovalCommandService`** = entry `saveKlaim` (CSRF guard + load + pic-guard `kepegawaian-s5n` + dispatch 5-periode + update chain pointer) ~60 baris — paralel `CutiApprovalCommandService.savePengajuan`; **(3) `CutiApproveKlaimCutiService`** = settlement **dalam-tahun** (`between1JanAnd30Jun`/`between1JulAnd31Dec`/`between30JunAnd1Jul` + `updateKuotaCuti`) ~110 baris; **(4) `CutiKlaimCrossYearSettlement`** = settlement **lintas-tahun** (`forNextYear`/`overlappingYear`/`separateCutiWithNextYear`) ~75 baris. Seam (3)-vs-(4) = batas domain nyata (kelola 1 tahun kuota vs 2 tahun + `riwayatKuota0/1` paralel), bukan abstraksi buatan. **Catatan penamaan**: meski §17 rename trio command jadi `Cuti<Operasi>CommandService`, settlement-math (3)(4) **bukan** entry Command/Query — kelas kolaborator helper (seperti `SaveCutiService`/`CutiKuotaUpdateByCutiService`), dipanggil dari `CutiKlaimApprovalCommandService`.

- **Alokasi kuota sisi klaim (`CutiApproveKlaimCutiService`) → port 1:1**. Klaim **bukan** pemakaian ulang allocator reservasi — semantik berbeda (settle vs reservasi). Dispatch periode **5-cara** kini triplikat, dibiarkan per stance parity. **Tiga bug klaim dipertahankan, masing-masing dilacak beads issue terpisah**:
  1. `forNextYear:22` pakai `getTanggalMulai().getYear() − 1` (asimetri vs `overlappingYear:29`).
  2. `between1JanAnd30Jun:46` pakai `LocalDate.now()` — outcome approval tergantung kapan tombol diklik.
  3. `saveKlaim:222` bandingkan `picSaatIni.equals(approver.getJabatan())` pada referensi entity (rapuh di bawah proxy Hibernate); `savePengajuan` bandingkan via `.getId()`.
  Catatan: exception-swallowing `saveKlaim` (`try{…}catch(Exception){FAILED}`) **bukan** termasuk yang dipertahankan — sudah masuk lingkup rework approval-Command (entry `@Transactional` tunggal).

- **Klasifikasi periode (5-cara) → ekstrak `CutiPeriodClassifier` murni; tindakan TIDAK dilebur**. Blok if-else 5-cabang **literal identik** di tiga titik: `PengajuanCutiCommand.save:73-85`, `.update:133-143`, `KlaimCutiCommand.saveKlaim:159-171` (kondisi: `startYear>now&&endYear>now`→NEXT_YEAR; `startYear==now&&endYear>start`→OVERLAPPING; `isBetweenDates(...,1,6,30)`→JAN_JUN; `isBetweenDates(...,7,12,31)`→JUL_DES; `isOverlappingDates(...)`→JUN_JUL). **Hanya bagian klasifikasi yang diekstrak** (sesuai arahan: pecah yang identik, pertahankan yang beda): `CutiPeriodClassifier.classify(tglMulai, tglSelesai, nowYear) → ECutiPeriod{NEXT_YEAR,OVERLAPPING,JAN_JUN,JUL_DES,JUN_JUL}` — fungsi murni statik, `nowYear` **di-inject sbg argumen** (bukan `LocalDate.now()` internal) supaya testable & memberi satu rumah utk fix bug cross-year `now()`. **Yang BERBEDA dipertahankan, tidak dilebur**: (a) target tiap bucket beda semantik — `save`/`update`→`saveCutiService.X(request,entity)` (reservasi, kurangi kuota), `saveKlaim`→`this.X(cutiPegawai,approval)` (settlement, catat realisasi); (b) **else-branch beda**: `save`&`saveKlaim`→`throw "Invalid request"`, `update`→**no-op diam** (suspect-bug, dilacak beads — jangan "diperbaiki" diam-diam saat port); (c) sumber tanggal beda (`request` vs `cutiPegawai`); (d) cabang non-tahunan (`saveCutiNonTahunan`) hanya di `save`/`update`. Tiap caller `switch(period)` ke target sendiri. **Efek ukuran `PengajuanCutiCommand`** (161→<120): dispatch 13-baris×2 jadi `switch` ringkas; +§47 hapus `setJumlahHari/HariKerja` double-subtract (4 baris); +§2/§27 pointer-init chain (87-96) pindah ke `CutiApprovalChainGenerator`. ⚠️ Buat beads issue utk `update` no-op else-branch (suspect-bug, tidak diperbaiki tanpa konfirmasi).

- **Validator pengajuan vs klaim → pecah dua kelas per seam operasi** (tegakkan 120 ketat). Legacy `CutiPengajuanValidator` (123 baris) punya dua metode konteks-berbeda: `validate(CutiPengajuanPostRequest)` guard pengajuan (59 baris: cek pending/exclusion/quota) + `validateKlaim(CutiPengajuanKlaimPostRequest)` guard klaim (36 baris: cek ref approved/no duplicate/no pending ibadah). Keputusan: **pecah jadi dua validator** — `CutiPengajuanValidator` pertahankan `validate` pengajuan, **`CutiKlaimValidator`** baru ambil `validateKlaim` klaim. Seam semantik jelas (validasi operasi berbeda), masing-masing <70 baris dengan overhead. Shared dependencies (`CutiPegawaiRepository`, `CutiJenisRepository`, `CutiKuotaQueryRepository`, `CutiProperties`) di-inject ke kedua kelas.

- **Approval state-machine → full §32 ADR-0021 restrukturisasi + ekstrak helper transisi** (tegakkan 120 ketat). `ApprovalCutiCommand` (121 baris) punya entry `savePengajuan` + dua helper (`doSaveAcceptReject`, `rejectCutiPegawai`) dengan **7 manual `save()` calls**. **Verifikasi lifecycle entity**: `cutiApproval` dibuat via `toEntity()` = NEW (butuh persist), `cutiPegawai`/chains di-load via repo = MANAGED (dirty-check otomatis). Keputusan: **(1) Buang 5 `save()` redundan** untuk managed entities (lines 92-94, 101-102, 113, 118), **pertahankan 3 `save(cutiApproval)`** untuk new entity (91, 100, 112); **(2) Ekstrak helper transisi murni** — `advanceChainPointer(currentChain, nextChain, cutiPegawai, status)` (update pointer: current→READ, next→WRITE, set picSaatIni) + `terminateChain(currentChain, cutiPegawai, status)` (terminal state: chain→READ, set approvalCutiStatus) — state mutation tanpa persistence; **(3) Rename `validateToken`→`isTokenAlreadyUsed`** (selaras §33). Hasil: file turun 121→~105 baris (hapus 5 + ekstrak 2 helper ~10 overhead, simplify caller), transisi state jadi **eksplisit** & **testable**.

- **JOOQ query repository → ekstrak mapper wajib; pure SQL logic boleh >120** (relax kondisional per §12). `CutiPengajuanQueryRepository` (347 baris) punya SELECT/JOIN kompleks 20+ fields 5+ JOINs (lines 54-92, 114-152, 170-208) + WHERE-building `baseWhere` (212-244) + **mapper methods ~91 baris** (256-346: `mapToResponse`, `mapToMiniResponse`, `mapCommonFields`, enum converters). **Kondisi relax 120 untuk `*QueryRepository`**: **hanya jika pure SQL logic** (SELECT/JOIN/WHERE construction inherently verbose). **Mapper WAJIB diekstrak** (§12 Pola B mapper). Keputusan: **(1) Ekstrak mapper** lines 256-346 → `CutiPegawaiJooqMapper` (Pola B: `final` static class, private constructor, NOT `@Component`); **(2) Remaining ~257 baris pure SQL** (query construction, WHERE-building) **acceptable** — ignore overrun untuk kategori ini; **(3) Query builder extraction** untuk deduplikasi SELECT/JOIN (3× identik) **optional** (readability, bukan mandatory). **Verifikasi read-model separation**: `CutiInboxQueryRepository` (112 baris, <120) sudah terpisah — inbox approval vs pengajuan queries = concern berbeda, konfirmasi proper split. **Prinsip umum**: JOOQ repos dengan pure SQL boleh >120; mapper/converter logic harus selalu dipisah.

- **JOOQ kuota repository → ekstrak mapper, accept SQL overrun**. `CutiKuotaQueryRepository` (208 baris) punya tiga query methods dengan SELECT triplikasi (lines 44-57 pageQuery main, 75-88 pageQuery additional, 107-120 getById — SELECT 13 fields 5 JOINs identik) + `baseWhere` helper (162-180, 19 baris) + **mapper method ~26 baris** (182-207: `mapToResponse`). ## Revisi (2026-07-09) — Inbox N+1 & shared selects

- **[SUPERSEDE mekanik collapse inbox] `GROUP BY ref_cuti_id` + `max()` → `QUALIFY ROW_NUMBER()`**. Entry lama ("Sisi baca → JOOQ penuh + mini-projection") menetapkan inbox pakai `GROUP BY ref_cuti_id` + `max(read_write_status)`. **Ditolak & diganti.** Alasan: satu pengajuan punya banyak baris `cuti_approval_chain` (satu per level); mekanik lama di `CutiInboxQueryRepository:40-48` pakai **tiga `DSL.max` terpisah** (`max(ID)`, `max(APPROVAL_LEVEL)`, `max(READ_WRITE_STATUS)`) yang **bisa mencampur nilai dari baris fisik berbeda** (bug halus — `id` dari baris A, `read_write_status` dari baris B). Selain itu tiap baris hasil memanggil `pengajuanQueryRepository.getById(refCutiId)` (7-join `fetchOne` per row) = **N+1** (21 query untuk 1 halaman 20 baris). **Keputusan**: collapse baris chain via `ROW_NUMBER() OVER (PARTITION BY REF_CUTI_ID ORDER BY APPROVAL_LEVEL DESC, ID DESC) = 1` (jOOQ `QUALIFY`, otomatis diterjemahkan ke **derived table** untuk dialect MariaDB — dikonfirmasi via context7, jOOQ 3.19.30 + MariaDBDialect; MariaDB 10.2+ mendukung window function & derived table). Baris representatif = **approval-level tertinggi** di antara baris chain **milik jabatan viewer** (WHERE `JABATAN_ID` sudah memfilter sebelum `ROW_NUMBER`, jadi semantiknya "level tertinggi di antara tugas approval si viewer" — benar secara domain). Semua kolom (`id`, `approval_level`, `read_write_status`) dijamin datang dari **satu baris fisik yang sama**. Pengajuan penuh di-JOIN di **query yang sama** (hilangkan `getById` per-row).

- **[SUPERSEDE status ekstraksi: optional → MANDATORY] Ekstrak `CutiPegawaiSelects` sebagai fondasi bersama**. Entry lama ("JOOQ query repository") menandai query-builder extraction sebagai *optional (readability)* dan mengonfirmasi `CutiInboxQueryRepository` sebagai *proper split terpisah*. **Direvisi.** Daftar 7-join + ~29 kolom ber-alias saat ini **di-copy-paste 3×** di `CutiPengajuanQueryRepository` (`pageQuery` 47-85, `getById` 106-144, `getMiniById` 176-213); bila inbox ikut menyalin → 4× duplikasi. **Keputusan**: ekstrak ke `CutiPegawaiSelects` (ikut master-pattern §2 & Template Selects) — satu `public static final Field<?>[] CUTI_PEGAWAI_COLUMNS` + field ber-alias (`ORG_ID`, `JAB_ID`, `JC_ID`, `SJC_ID`, `PIC_ID`, dst.) + satu helper JOIN. **Alias WAJIB dipertahankan persis** (`org_id`/`org_kode`/`org_nama`, `jab_id`/`jab_kode`/`jab_nama`, `jc_id`/`jc_nama`, `sjc_id`/`sjc_nama`, `pic_id`/`pic_kode`/`pic_nama`) karena `CutiPegawaiJooqMapper.populateFromRecord` membaca nested object via **string alias** tsb (kolom root dibaca via typed `CUTI_PEGAWAI.XXX`). `CutiPengajuan` **dan** `CutiInbox` sama-sama pakai `CutiPegawaiSelects` + reuse `CutiPegawaiJooqMapper.mapToResponse` untuk bagian pengajuan. - **[Count inbox → pertahankan `countDistinct(REF_CUTI_ID)`, jangan bungkus subquery QUALIFY]**.
