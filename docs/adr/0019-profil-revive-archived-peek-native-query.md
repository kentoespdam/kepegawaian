# Profil revive-on-create peeks the archived row via a native query, not a derived finder or JOOQ

On the profil write side, reviving a soft-deleted **Pendidikan** or **Kartu Identitas** when a deleted natural key is re-created requires reading the archived (`is_deleted = true`) row first. That peek uses a **native JPA `@Query` (`nativeQuery = true`) returning the mapped managed entity** — added per repository (`PendidikanRepository`, `KartuIdentitasRepository`). It is **not** a Spring Data derived finder (e.g. `findFirstBy...AndIsDeletedTrue` as used in master's `ProfesiCommandService`) and **not** a JOOQ query. The returned managed `@Audited` entity is revived in the same write transaction via `setIsDeleted(false)` + apply-fields + `save()`, which produces an Envers revision.

**Why:** master's `Profesi` carries only `@SQLDelete` (no `@SQLRestriction`), so a plain derived finder can still see archived rows and master's revive works. The profil entities `Pendidikan` and `KartuIdentitas` carry **both** `@SQLDelete` **and** `@SQLRestriction("is_deleted = FALSE")`. Hibernate appends `AND is_deleted = false` to every HQL/JPQL/derived query — including `findById` SELECT-by-PK — so any finder filtering for `is_deleted = true` becomes `WHERE is_deleted = true AND is_deleted = false`, which is **always empty**. Copying master's derived-finder revive verbatim would therefore return empty **with no error** — a silent trap (this is exactly what prompted the "why not JOOQ?" question). Two alternatives were rejected: (a) removing `@SQLRestriction` from the entities — large blast radius, every existing query would need manual `is_deleted` filtering; (b) a JOOQ peek — JOOQ bypasses `@SQLRestriction` but returns a flat record/projection, not a managed `@Audited` entity, so the revive could not go through `save()` and would produce **no Envers revision**. A native `@Query` is the only option that bypasses `@SQLRestriction` *and* returns a Spring-Data-managed entity that is revivable into a proper revision. In-repo precedent exists: `PendidikanRepository.rollbackPrevVersion(...)` already uses a native column-by-column UPDATE to bypass `@SQLRestriction`.

**Consequence:** each of the two repositories gains a native peek finder returning a managed `Pendidikan` / `KartuIdentitas`; the command side stays single-technology (JPA on writes, JOOQ confined to the read/query side — consistent with [ADR-0001](0001-jpa-write-jooq-read-cqrs.md) and [ADR-0017](0017-jooq-read-into-repository-layer.md)). The revived write is tagged **INSERT** (`tambah`), not UPDATE: when a pegawai re-adds and SDM **rejects**, the row is hard-deleted permanently so the key is freed for a fresh retry — it is not reverted to archived state (see CONTEXT.md "membuat ulang data Profil"). The archived row's prior Envers history is retained in the audit table regardless. Relates to [ADR-0003](0003-envers-scoped-to-penggajian-kepegawaian.md) (Envers scope — every revive `save()` is a revision), [ADR-0005](0005-revive-on-create-soft-delete-unique.md) (the master revive-on-create pattern this adapts), and [ADR-0018](0018-changedstatus-server-resolved-by-role.md) (the INSERT/reject queue semantics).
