# changedStatus is server-resolved by role, not sent by the client

On the profil write side, `changedStatus` is no longer a request field. It is decided server-side by a single `@Component ChangedStatusResolver`, injected into every profil `CommandService` (all 8 entities: biodata, pendidikan, keahlian, keluarga, pelatihan, pengalamanKerja, kartuIdentitas, lampiranProfil). The resolver reads the principal (`AppwriteUser.getAuthorities()`) and returns `false` when the writer holds `ROLE_SDM` (the change is immediately stable, no approval queued) and `true` otherwise (the change waits for SDM approval). The `changed_status` field is removed from every profil `PostRequest`/`PutRequest`.

**Why:** in the legacy code `changedStatus` was set straight from the request body (`entity.setChangedStatus(request.getChanged_status())` in the DTO `from(...)` methods). That let any caller send `changed_status=false` to push a change directly to stable without SDM approval — an approval-bypass security hole. The flag does **not** control history (see below), so a client setting it was never about auditing; it only decided whether the change needed sign-off, which is exactly the decision a client must not make. Centralizing the rule in one resolver keeps the role logic in a single place and gives the planned per-entity RBAC one seam to replace instead of eight.

**Consequence:** this is a **breaking API contract change** — clients still sending `changed_status` must drop it; reintroducing the field would reopen the bypass. `changedStatus` gates only the **ProfileUpdate approval queue**, not the **Envers history**: profil entities are `@Audited`, so every write records a revision regardless of role or `changedStatus`. An SDM edit (`changedStatus=false`) therefore keeps full Envers history and merely skips queuing an approval for itself; revert still reads those revisions. The resolver's `ROLE_SDM` check is a single-role placeholder for the planned **per-entity RBAC** (out of scope for the profil rewrite). Approval/reject and revert logic live entirely in the `updateProfile` module; the profil write side only triggers queue creation via `profileUpdateService.create(...)` (one-way dependency profil → updateProfile). Relates to ADR-0003 (Envers scope) and ADR-0016 (profile-conditional auth).
